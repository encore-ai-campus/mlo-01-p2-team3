# 데이터 품질 진단 및 기준

## 1. 목적

API 원본과 Bronze·정규화 결과·Silver·Gold 사이의 품질을 측정하고, 운영 실행별 결과를 비교한다.

## 2. 진단 기준과 운영 수치

| 항목 | 기준 |
|---|---|
| 논리 원본 필드 목록 | 17개(필수 API 본문 데이터 15개 + 선택 응답 메타데이터 2개) |
| 운영 입력 | API JSON 페이지 |
| 운영 건수 | run_id별 hr_pipeline_runs와 실제 컬렉션에서 계산 |
| 과거 샘플 수치 | 규칙 설계 참고용으로만 보관하며 현재 운영 수치로 사용하지 않음 |

운영 수치는 데이터가 갱신될 때마다 달라질 수 있으므로 문서에 고정하지 않는다.
Bronze·Silver·Review·Gold의 현재 건수는 품질 보고서 파일과 실행 이력에서 확인한다.
Silver 보고서는 scripts/report_silver_quality.py가 생성하고, Gold 결과는 hr_gold_load_batch에 남긴다.

## 3. 확인된 문제

| 영역 | 예시 | 처리 방향 |
|---|---|---|
| ID | 하이픈·밑줄·공백·소문자 | 정규화 후 패턴 검사 |
| 이름·부서·직급 | 앞뒤 공백·내부 공백·오류값 | 공백 정리, 모호하면 검토 |
| 날짜 | ISO·슬래시·점·14자리·비정상 날짜 | 승인 형식만 해석 |
| 상태 | `사용`, `재직`, `미사용`, `UNKNOWN` | 별칭 매핑, 미등록값 검토 |
| 동일 ID 반복 수신 | 여러 배치에서 같은 ID가 반복됨 | 본문 데이터가 다르면 검토 |
| 조직 관계 | 부모 누락·자기 참조·순환·변경 후보 | 최상위/하위 기준과 FK·계층 검사 |

조직 관계는 다음 기준으로 진단한다.

- `area_id == top_area_id`이면 최상위 부서로 보고, 부모가 없거나 자기 자신을 가리켜도 정상이다.
- `area_id != top_area_id`이면 하위 부서로 보고, 존재하는 다른 부서를 부모로 지정해야 한다.
- 하위 부서의 부모 누락·자기 참조·순환 연결은 검토 큐 건수로 집계한다.
- 같은 `area_id`의 명칭·상위 부서 정보 변경이나 `area_id` 변경은 변경 후보로 집계한다.
- 관련 코드·명이 일관되게 변경된 경우에는 이동 갱신으로, 그렇지 않으면 검토 대상으로 집계한다.

## 4. 품질 지표

| 코드 | 의미 | 목표 |
|---|---|---:|
| `SCHEMA_RATE` | 필수 API 본문 데이터 15개 계약 준수율과 제공된 선택 응답 메타데이터 보존율 | 100% |
| `SOURCE_LOSS_COUNT` | API 원본 문서의 본문 데이터·응답 메타데이터 유실 | 0 |
| `BRONZE_COUNT_DIFF` | API 원본 항목 수와 Bronze 저장 건수의 설명되지 않은 차이 | 0 |
| `BRONZE_HASH_MISMATCH` | 저장된 원본 해시와 수집 시 해시의 불일치 | 0 |
| `BRONZE_RUN_LINK_ERROR` | Bronze 원본과 `run_id` 실행 이력의 연결 누락 | 0 |
| `NORMALIZATION_PASS_COUNT` | 형식 정규화를 통과한 건수 | 전부 사유 설명 |
| `NORMALIZATION_REVIEW_COUNT` | 정규화 또는 도메인 검증 실패 건수 | 전부 검토 |
| `ID_VALID_RATE` | 조직·담당자 ID 패턴 적합률 | 100% 또는 승인 예외 |
| `DATE_PARSE_RATE` | 날짜 해석 성공률 | 100% 또는 승인 예외 |
| `DOMAIN_VALID_RATE` | 상태·조직 레벨 허용값 적합률 | 100% |
| `EQUIVALENT_DUP_COUNT` | 표준 결과가 같은 중복 | 전부 이력 설명 |
| `SAME_ID_CONFLICT_COUNT` | 동일 업무 ID의 API 본문 데이터 충돌 수 | 전부 검토 |
| `HIERARCHY_REVIEW_COUNT` | 부모·최상위 관계 판단이 필요한 건수 | 전부 검토 |
| `RECON_DIFF` | 계층 간 설명되지 않은 차이 | Gold 연동 단계에서 산출 |

## 5. 실행별 기록

| run_id | pages | bronze_saved | status |
|---|---:|---:|---|
| `<배치 ID>` | `<값>` | `<값>` | `COMPLETED` |

Silver 정제 결과는 실행 시 출력되는 `정제된 건수`와 `정제되지 않은 건수`로 별도 확인한다.

## 6. 계층별 확인

| 비교 | 확인 내용 |
|---|---|
| API ↔ Bronze | 레코드 수·응답 메타데이터(있을 때)·본문 데이터·논리 목록 17개·원본값·`run_id` 추적 |
| Bronze ↔ 정규화 결과 | 업무 15개 대응·형식 정규화 건수 |
| 정규화 결과 ↔ Silver | 도메인·중복·조직 관계·검토 건수 |
| Silver ↔ Gold | 승인 건수·PK/FK·현재값 |
| Gold ↔ Django | 조직·담당자·품질 지표 |

Bronze 무결성은 API→Bronze 비교에서 별도로 집계한다. 차이가 있으면 Silver 정제 건수에 포함하지 않고
실행·페이지 실패 사유로 기록한다. API 수집 소스와 Silver 검증 소스는 분리하므로, 이 지표를 추가해도 수집 원문은 바뀌지 않는다.

## 7. 대시보드 지표

- 전체 조직 수와 최상위 조직 수
- 조직별 담당자 수
- 재직·퇴직 담당자 수
- 부서·직급별 담당자 수
- 오류·검토·충돌 건수
- 정규화 실패·도메인 검증 실패 건수
- 최근 API 성공·실패·지연 건수

## 8. 완료 기준

- 실행별 지표와 실행 이력이 존재한다.
- 중복·충돌·날짜·상태·계층 오류를 구분한다.
- 동일 ID 충돌 데이터가 기존 정상값을 자동 변경하지 않는다.
- 모든 건수 차이를 사유 코드로 설명할 수 있다.

## 9. 현재 Django 출력 점검

Gold에서 화면으로 전달되는 값은 다음처럼 확인한다.

- 조직코드와 조직명이 서로 다른 열에 있는지 확인한다.
- 담당자코드와 담당자명이 서로 다른 열에 있는지 확인한다.
- 화면 검색 결과와 전체 CSV의 행 수가 각각 같은 조회 조건의 Gold 결과와 일치하는지 확인한다.
- 조직 CSV는 /hrdata/areas/export.csv, 담당자 CSV는 /hrdata/managers/export.csv를 사용한다.
- 주소에 all=1을 붙인 전체 CSV가 화면의 현재 페이지 수가 아니라 전체 결과를 포함하는지 확인한다.
- 이름 반복 단어·공백 정리는 표시값만 바꾸며, ID·원본명·행 수는 바뀌지 않는지 확인한다.
