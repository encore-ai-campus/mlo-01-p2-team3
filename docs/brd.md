# BRD

## 레거시 인사·조직 데이터 표준화 및 조회 솔루션

## 1. 프로젝트 개요

### 프로젝트명

**레거시 인사·조직 데이터 표준화 및 조회 솔루션**

### 추진 배경

레거시 인사·조직 데이터는 필드명과 값 형식이 일정하지 않아 부서 관계와 관리자 정보를 정확하게 확인하기 어렵다.

### 해결하려는 문제

- 부서·부모 부서·최상위 부서 관계 확인이 어려움
- 관리자 정보와 재직 상태를 일관되게 조회하기 어려움
- 오류 데이터와 판단할 수 없는 데이터를 구분하기 어려움
- 정제 과정에서 원본 데이터가 유실될 가능성이 있음
- 조직 정보를 한 화면에서 확인하기 어려움

### 프로젝트 목적

레거시 인사·조직 데이터를 표준화하고, 검증된 조직 정보를 조회할 수 있는 대시보드를 제공한다.

### 기대 효과

- 조직 정보 조회 편의성 향상
- 부서 계층 관계 명확화
- 관리자 정보 확인 효율 향상
- 오류 데이터 관리 용이
- 원본 데이터 유실 방지
- 조직 데이터 활용성과 신뢰성 향상

## 2. 비즈니스 목표

- 레거시 조직 데이터를 일관된 형식으로 제공한다.
- 부서와 부모 부서, 최상위 부서의 관계를 명확하게 확인할 수 있게 한다.
- 부서별 관리자 정보와 재직 상태를 조회할 수 있게 한다.
- 데이터 오류와 판단할 수 없는 데이터를 별도로 확인할 수 있게 한다.
- 원본 데이터의 유실 없이 정제 결과를 관리한다.
- 검증된 조직 정보를 대시보드에서 빠르게 조회할 수 있게 한다.
- 향후 조직 계층이 변경되어도 데이터를 계속 활용할 수 있게 한다.

## 3. 대상 조직

### 인사·조직 부서

- 표준화된 부서·관리자·조직 계층 정보를 한 곳에서 확인할 수 있게 된다.
- 조직 변경 사항을 빠르게 파악할 수 있게 된다.

### 각 업무 부서

- 소속 부서와 상위 부서 관계를 바로 파악할 수 있게 된다.
- 담당 관리자와 재직 상태를 쉽게 확인할 수 있게 된다.

### 데이터 품질 관리 부서

- 오류·판단 불가 데이터를 별도로 파악할 수 있게 된다.
- 검토·재처리 상태를 추적할 수 있게 된다.

### 데이터 파이프라인 운영 부서

- API 수집과 데이터 처리 상태를 한눈에 파악할 수 있게 된다.
- 실패 원인과 실행 이력을 추적할 수 있게 된다.

### 조직 정보 조회 부서

- 검증된 조직 정보를 빠르게 검색할 수 있게 된다.
- 대시보드에서 조직 현황을 쉽게 파악할 수 있게 된다.

## 4. 업무 범위

### 포함 범위

- API를 통한 레거시 인사·조직 데이터 수집
- 수집한 원본 데이터 보존
- 조직·관리자 데이터 표준화 및 정규화
- 중복·오류·판단 불가 데이터 분리
- 부모 부서와 최상위 부서 관계 관리
- 검토 대상 데이터 승인 및 재처리
- 검증된 데이터의 Gold 제공
- Django 기반 조직 정보 대시보드 제공
- 데이터 수집·정제·검토 결과 확인

### 제외 범위

- 급여·근태·평가 데이터 관리
- 채용·퇴사 업무 처리
- 개인 연락처 관리
- 기존 인사 시스템 자체 대체
- 판단 불가 데이터의 자동 추정
- AI 모델 학습 및 추천 기능
- 원본 데이터 삭제 또는 임의 수정

## 5. 목표 업무 흐름

```text
API 데이터 수집
      ↓
Bronze 원본 보존
      ↓
Silver 표준화·검증
      ├─ 정상 데이터 → Gold
      └─ 오류·판단 불가 → 검토 큐
      ↓
Django 조직 정보 대시보드
```

## 6. 주요 비즈니스 요구사항

### 데이터 수집

- API를 통해 데이터를 주기적으로 수집한다.
- 수집 실패와 실행 상태를 확인할 수 있어야 한다.
- 원본 데이터는 정제 여부와 관계없이 보존한다.

### 데이터 표준화

- 조직·관리자 필드명을 표준 형식으로 통일한다.
- 날짜·ID·상태·조직 레벨 값을 표준화한다.
- Silver 데이터는 정해진 표준 필드 기준을 따른다.

### 오류 및 검토

- 자동으로 판단할 수 없는 데이터는 삭제하지 않는다.
- 오류 데이터는 검토 큐에서 별도로 관리한다.
- 담당자의 승인이나 수정 후 다시 처리할 수 있어야 한다.
- 처리 결과와 검토 이력을 확인할 수 있어야 한다.

### 조직 관계

- `parent_area`는 바로 위 부모 부서로 관리한다.
- `top_area`는 최상위 부서로 관리한다.
- 향후 상위 부서가 추가되어도 관계를 갱신할 수 있어야 한다.
- 부모 관계가 잘못되거나 확인되지 않으면 검토 대상으로 분류한다.

### 조회 및 대시보드

- 조직별 부서 정보를 조회할 수 있어야 한다.
- 최상위·하위 부서를 구분할 수 있어야 한다.
- 부서별 관리자 정보를 확인할 수 있어야 한다.
- 데이터 품질과 검토 현황을 확인할 수 있어야 한다.
- 최근 수집 상태와 처리 결과를 확인할 수 있어야 한다.

## 7. 데이터 계층 원칙

```text
Bronze: 원본 보존
Silver: 표준화·검증
Gold: 조회·분석용 데이터
```

각 계층은 다음 목적을 가진다.

- Bronze: 수집한 원본을 보존한다.
- Silver: 표준화와 검증을 완료한 데이터를 관리한다.
- Gold: 조회와 분석에 필요한 데이터를 제공한다.

BRD에서는 각 계층의 목적만 설명하고, 실제 컬렉션명·Python 파일명·YAML 문법은 PRD와 기술 문서에서 정의한다.

## 8. 성공 기준

- 원본 데이터가 누락 없이 보존된다.
- 표준화된 조직 정보를 조회할 수 있다.
- 오류 데이터가 별도로 확인된다.
- 조직 계층 관계를 정확히 확인할 수 있다.
- Gold에는 검증된 데이터만 제공된다.
- 수집·정제·검토 결과를 추적할 수 있다.
- 사용자가 대시보드에서 필요한 조직 정보를 빠르게 확인할 수 있다.

## 9. 제약

- 실제 원본은 API JSON으로 제공된다.
- 판단할 수 없는 데이터를 자동으로 추정하지 않는다.
- Bronze 원본은 삭제하지 않는다.
